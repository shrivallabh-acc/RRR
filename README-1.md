# RRR — Release Readiness Results: Complete Operations Guide

> **What this is:** An AI-first, local-first CLI that reads your weekly RKT Program Metrics
> HTML export, combines it with environment, dependency, and operational data you provide, and
> produces a deterministic **GO / NO_GO / CONDITIONAL / INCOMPLETE** verdict with a 0–100 score,
> per-dimension evidence, risk factors, and a remediation action plan.
>
> Everything runs on your machine by default. No cloud calls, no API keys required for the
> standard configuration. Phase 2 opt-in providers (Amazon Bedrock, Anthropic Claude API) are
> available for AI-written narrative — see [Section 11](#11-llm-providers).

## 1. System overview

```
┌─────────────────────────────────────────────────────────────────────┐
│  INPUTS                                                             │
│                                                                     │
│  input/RKT Program Metrics Report.html   ← weekly export from RKT  │
│  data/environment.json                   ← you maintain             │
│  data/dependency.json                    ← you maintain             │
│  data/operational.json                   ← you maintain             │
│  configs/osm.yaml                        ← you create once          │
└────────────────────┬────────────────────────────────────────────────┘
                     │
          ┌──────────▼──────────┐
          │    rrr-ingest       │  Step 1 — run weekly after saving HTML
          │  (one-time / weekly)│
          └──────────┬──────────┘
                     │
          brain/OSM-history.json   ← normalised, versioned snapshot
                     │
          ┌──────────▼──────────┐
          │   rrr --release "…" │  Step 2 — run per release, as often as needed
          │  (assessment engine)│
          └──────────┬──────────┘
                     │
┌────────────────────▼────────────────────────────────────────────────┐
│  OUTPUTS                                                            │
│                                                                     │
│  stdout          VERDICT: NO_GO  SCORE: 62  CONFIDENCE: 100%       │
│  --format json   full JSON (scores, evidence, risk factors)         │
│  --format markdown   rendered report (Confluence / PR comment)      │
│  --format plan   action-plan checklist (Jira / release tracker)     │
│  data/local/rrr.sqlite   persisted history + trend tracking         │
└─────────────────────────────────────────────────────────────────────┘
```

### Three entry points, one pipeline

| Command | Does what |
|---------|-----------|
| `rrr-ingest` | Reads one or more RKT HTML reports, extracts all release data, writes `brain/<vs>-history.json`. Run weekly. |
| `rrr` | Runs the six-dimension assessment for one named release, produces the verdict. Run on demand. |
| `rrr-ui` | Launches the NiceGUI web dashboard — release browser, history panel, and score-over-time trends. Run on demand. |

The score is **deterministic** — same inputs always produce the same number. The LLM (if enabled)
writes only the narrative rationale; it never influences the numeric result.

## 4. Inputs — what you need to provide

### 4.1 RKT Program Metrics HTML report

The weekly HTML export from the RKT Program Metrics tool. Save the **full page** (not a PDF or
screenshot) to your `input\` directory. One file per weekly cycle is the normal cadence.

**What the HTML contains:**
- 41 release records (for OSM), each with story-point data, defect trends, code quality scores,
  E2E test results, and planned-value curves
- All releases across all programmes covered by the tool (OSM, AIMS, PIMS, EIMS, R5, R6, ME&Q, NEO, R@W)
- No separate `programme` field — programme codes are embedded in the release name string

**What it does NOT contain:**
- Infrastructure / environment status
- External dependency health
- Team ownership or launch dates (per release)

These must come from you via `environment.json` and `dependency.json`.

---

### 4.2 `data/environment.json` — infrastructure readiness

Describes the current provisioning and stability state of your infrastructure components
**at the time of the release**. You update this file before each assessment run.

```json
{
  "schema_version": "1.0.0",
  "release": "RetirePlus RC/RCP Enrollment",
  "captured_at": "2026-06-22T10:00:00.000Z",
  "components": [
    { "name": "app-server",   "provisioning": "validated",   "stability": "stable"   },
    { "name": "database",     "provisioning": "configured",  "stability": "stable"   },
    { "name": "load-balancer","provisioning": "provisioned", "stability": "degraded" },
    { "name": "cache",        "provisioning": "missing",     "stability": "stable"   }
  ]
}
```

**`provisioning`** — drives the environment *score* (higher = more ready):

| Value | Score contribution | Meaning |
|-------|--------------------|---------|
| `validated` | 1.00 | Fully signed off and verified |
| `configured` | 0.75 | Set up but not yet formally validated |
| `provisioned` | 0.50 | Allocated but not configured |
| `missing` | 0.00 | Not yet provisioned |

**`stability`** — drives *risk severity*, not the numeric score:

| Value | Risk raised | Gate effect |
|-------|-------------|-------------|
| `down` | CRITICAL risk factor | Forces NO_GO regardless of score |
| `degraded` | MAJOR risk factor | Caps verdict at CONDITIONAL |
| `stable` | MINOR risk factor | No gate effect |

> **Key insight:** A `validated` (score 1.00) component that is `down` still scores 1.00 but
> raises a CRITICAL risk and triggers NO_GO. Provisioning readiness and operational stability
> are tracked independently.

**CSV alternative** — same data, one component per row:
```
name,provisioning,stability,notes
app-server,validated,stable,
database,configured,stable,awaiting sign-off
```

---

### 4.3 `data/dependency.json` — upstream dependency status

Describes the completion and integration-validation state of every external dependency your
release requires. You update this before each assessment run.

```json
{
  "schema_version": "1.0.0",
  "release": "RetirePlus RC/RCP Enrollment",
  "captured_at": "2026-06-22T10:00:00.000Z",
  "dependencies": [
    { "name": "payments-api-v2",    "completion": "complete",     "integration": "passed"        },
    { "name": "notification-hub",   "completion": "in_progress",  "integration": "not_validated" },
    { "name": "legacy-adapter",     "completion": "not_started",  "integration": "not_validated" }
  ]
}
```

**`completion`** ∈ `complete | in_progress | not_started`
**`integration`** ∈ `passed | not_validated | failed`

**Scoring:** `count(complete AND passed) / total dependencies`

**Risk classification per dependency:**

| Condition | Classification | Gate effect |
|-----------|---------------|-------------|
| `not_started` OR `integration == failed` | blocking | CONDITIONAL cap on verdict |
| `in_progress` AND `not_validated` | at_risk | Narrative only, no gate |
| All other cases | on_track | No effect |

**CSV alternative:**
```
name,completion,integration,owner,notes
payments-api-v2,complete,passed,Payments Team,
notification-hub,in_progress,not_validated,Platform Team,targeting next sprint
```

---

### 4.4 `data/operational.json` — deployment pipeline readiness

Describes the health of your deployment pipeline and rollback preparedness for this release.
Update this file before each assessment run.

```json
{
  "schema_version": "1.0.0",
  "release": "RetirePlus RC/RCP Enrollment",
  "deployment_pipeline": "green",
  "rollback_plan": "documented",
  "change_freeze": false,
  "recent_deployment_failures": 0,
  "deployment_duration_minutes": null
}
```

**`deployment_pipeline`** — drives 60% of the operational score:

| Value | Score contribution | Meaning |
|-------|--------------------|---------|
| `green` | 1.00 | All pipeline stages passing |
| `yellow` | 0.60 | Intermittent failures; builds eventually succeed |
| `red` | 0.00 | Pipeline is broken — builds failing |
| `unknown` | 0.50 | Status not known; confidence capped at 75% |

**`rollback_plan`** — drives the remaining 40% of the operational score:

| Value | Score contribution | Meaning |
|-------|--------------------|---------|
| `documented` | 1.00 | Rollback procedure fully written and tested |
| `partial` | 0.50 | Some documentation exists but incomplete |
| `none` | 0.00 | No rollback plan — MAJOR risk, CONDITIONAL cap |
| `unknown` | 0.50 | Status not known; confidence capped at 75% |

**Risk overrides:**

| Condition | Risk raised | Gate effect |
|-----------|-------------|-------------|
| `change_freeze: true` | CRITICAL | Forces NO_GO regardless of score |
| `deployment_pipeline: red` | CRITICAL | Forces NO_GO regardless of score |
| `deployment_pipeline: yellow` | MAJOR | Caps verdict at CONDITIONAL |
| `rollback_plan: none` | MAJOR | Caps verdict at CONDITIONAL |
| `recent_deployment_failures > 0` | MINOR | Narrative only, no gate |

> **Tip:** `deployment_duration_minutes` is optional and informational — the typical minutes
> a production deployment takes once the pipeline is green. Leave `null` if not yet deployed.

### 4.5 `configs/osm.yaml` — your value-stream config

A small YAML file that tells RRR where your data files live. Copy `configs/osm.yaml` as a
template and adjust for your value stream.

```yaml
# configs/osm.yaml
sources:
  brain:
    dir: "./brain"
    value_stream: "OSM"           # must match the --value-stream used in rrr-ingest
  environment: { type: file, path: "./data/environment.json" }
  dependency:  { type: file, path: "./data/dependency.json" }
  operational: { type: file, path: "./data/operational.json" }

thresholds:
  # List dimensions that must be available for a GO verdict.
  # Remove 'environment' if you don't yet have env data.
  required_dimensions: [test_readiness]
```

All other settings inherit from the bundled defaults. See [Section 12](#12-configuration-reference)
for every available knob.

## 5. Step-by-step operating flow

### Step 1 — Save the HTML report

Download the RKT Program Metrics HTML report for your value stream and save it to `input\`:

```
input\RKT Program Metrics Report.html
```

The filename does not matter — all `.html` files in the directory are processed.

---

### Step 2 — Ingest the HTML → brain JSON

```powershell
rrr-ingest --html-dir input --brain-dir brain --value-stream "OSM"
```

**Output:**
```
  RKT Program Metrics Report.html  →  snapshot 2026-06-19  (41 releases)  →  brain\OSM-history.json

Done: 1 file(s) ingested into brain\OSM-history.json
```

This creates or updates `brain\OSM-history.json`. Each HTML file becomes one dated snapshot.
Running the same file again is safe — it upserts on the snapshot date.

---

### Step 3 — Discover what releases are in the brain file

The HTML contains releases from multiple programmes (OSM, AIMS, PIMS, etc.). Use
`--list-releases` to see them all with their programme tags:

```powershell
rrr --list-releases --value-stream "OSM" --config configs/osm.yaml
```

```
  ...
```

**Filter to just your programme's releases:**

```powershell
rrr --list-releases --programme OSM --value-stream "OSM" --config configs/osm.yaml
```

---

### Step 4 — Update environment and dependency data

Edit `data\environment.json`, `data\dependency.json`, and `data\operational.json` to reflect
the **current state** for the release you're about to assess. See
[Section 4.2](#42-dataenvironmentjson--infrastructure-readiness),
[Section 4.3](#43-datadependencyjson--upstream-dependency-status), and
[Section 4.4](#44-dataoperationaljson--deployment-pipeline-readiness) for the schemas.

> **Important:** These files are not generated — you own them. Update them before every

```powershell

    --value-stream "OSM" `
```

## 6. `rrr-ingest` — CLI reference

Converts RKT Program Metrics HTML reports into `brain/*.json` history files.

```
rrr-ingest --html-dir <PATH> --brain-dir <PATH> --value-stream <TEXT> [--verbose]
```

### Flags

| Flag | Required | Default | Description |
|------|----------|---------|-------------|
| `--html-dir PATH` | Yes | — | Directory containing `.html` report file(s) |
| `--brain-dir PATH` | Yes | — | Output directory for the brain JSON history file (created if absent) |
| `--value-stream TEXT` | Yes | — | Value-stream name — becomes the filename prefix: `<value-stream>-history.json` |
| `--verbose` | No | off | Enable DEBUG-level logging to stderr |

### How it works

1. Scans `--html-dir` for all `.html` files (alphabetical order)
2. For each file: locates the embedded `const __REPORT__ = {...}` JSON literal
3. Maps each release to the brain contract schema (see [Section 4.1](#41-rkt-program-metrics-html-report))
4. Extracts the programme code from each `ir_name` (AIMS, PIMS, R5, etc.; `"OSM"` if untagged)
5. Parses enabler/dependency annotations from `ir_name` (`(Dependency for: X; Launch: Y)`)
6. Appends a dated snapshot to `<brain-dir>/<value-stream>-history.json` (upsert on date)

### What it extracts from the HTML

| Brain field | Source in HTML | Notes |
|-------------|---------------|-------|
| `ir_name` | `release.ir_name` | Direct copy |
| `programme` | Parsed from `ir_name` prefix/suffix | AIMS/PIMS/EIMS/R5/R6/ME&Q/NEO/R@W; `"OSM"` if no code |
| `release_relationship` | Parsed from `(Dependency for: X; Launch: Y)` in `ir_name` | Present on 2 of 41 releases |
| `summary` | `release.summary` | total/closed/remaining SP counts |
| `pv_latest` | Last non-null element of `release.pv.{pv,actual}` series | Future dates padded with null |
| `sq_avg` | Mean of `release.sq_caps.scores` × 1.5, clamped to 0–3 | HTML scores are 0–2 scale |
| `sq_below_1` | Capability names with score < 2/3 on the HTML scale | Quality risk flags |
| `defect_trend_last5` | Running cumulative open defects, last 5 data points | Never goes negative |
| `defects_open` | `release.defect_priority` matrix summed by priority column | blocker/critical/major/minor |
| `defects_closed_cumulative` | Sum of `release.defects_closed.values` | — |
| `e2e_latest` | Last non-null entry in `release.e2e_overall` series | Null if no E2E data |
| `weekly_last3` | Last 3 non-null entries of `release.weekly` | Velocity trend |

### Multiple HTML files (historical backfill)

Put multiple weekly HTML files in `--html-dir`. They are processed in filename order. Each
produces one snapshot with its own date; the history file accumulates all of them. Running
the same file a second time replaces its snapshot (idempotent).

```
input\
  2026-06-08 RKT Report.html    → snapshot 2026-06-08
  2026-06-15 RKT Report.html    → snapshot 2026-06-15
  2026-06-22 RKT Report.html    → snapshot 2026-06-22
```

```powershell
rrr-ingest --html-dir input --brain-dir brain --value-stream "OSM"
# Produces brain\OSM-history.json with 3 snapshots
# Scope-creep detection uses the earliest snapshot as the baseline
```

## 7. `rrr` — CLI reference

Runs the six-dimension assessment for one release and produces the verdict.

```
rrr --release <TEXT> [options]
rrr --list-releases [options]
```

### Flags

| Flag | Default | Description |
|------|---------|-------------|
| `--release TEXT` | — | Release name to assess. Supports fuzzy/partial matching. Required unless `--list-releases`. |
| `--config PATH` | bundled defaults | YAML config file. Values merge over bundled defaults — only override what you need. |
| `--value-stream TEXT` | config value | Overrides `sources.brain.value_stream`. Selects `<value-stream>-history.json`. |
| `--programme TEXT` | — | Filter by programme code (OSM, AIMS, PIMS, etc.). Scopes `--list-releases` output and narrows fuzzy `--release` matching. |
| `--format text\|json\|markdown\|plan` | `text` | Output format. See [Section 8](#8-outputs--where-results-go). |
| `--verbose` | off | Shorthand for `--format json`; also enables DEBUG-level logging to stderr. |
| `--dry-run` | off | Run the full assessment pipeline without writing to SQLite. |
| `--list-releases` | off | Print all releases in the brain file (with programme tags) and exit. No assessment runs. |

### Release name matching

`--release` does not require the exact name. The engine tries in order:

1. **Exact match** — `"RetirePlus RC/RCP Enrollment"` matches precisely
2. **Case-insensitive exact** — `"retireplus rc/rcp enrollment"` matches
3. **Case-insensitive substring** — `"RetirePlus"` matches if exactly one release contains it

If the substring matches **multiple** releases, the engine errors with a disambiguation list:

```
ERROR: 5 releases match 'Terminations Cash' — be more specific:
  Terminations Cash Withdrawals
  AIMS - Terminations Cash Withdrawals
  PIMS - Terminations Cash Withdrawals
  R5 IS - DT Terminations Cash Withdrawal
  Spousal Waiver - Terminations Cash Withdrawals
```

Resolve by adding `--programme OSM` to scope to one programme, or use the exact name from
`--list-releases`.

### Exit codes

Used by CI/CD pipelines to gate deployments:

| Code | Verdict | Meaning |
|------|---------|---------|
| `0` | GO | Release is ready |
| `1` | NO_GO | Release is blocked — do not deploy |
| `2` | CONDITIONAL | Release can proceed with caveats — review action plan |
| `3` | INCOMPLETE or ERROR | Assessment could not complete — check logs |

A `- [ ]` Markdown checklist bucketed by severity. Copy directly into Jira or your release tracker.

```powershell
rrr --release "RetirePlus RC/RCP Enrollment" `
    --config configs/osm.yaml `
    --format plan > reports\RetirePlus-action-plan-2026-06-22.md
```

```markdown

**Verdict: NO_GO  |  Score: 62  |  Confidence: 100%**

---

## CRITICAL — Must resolve before GO

- [ ] Open blocker defect detected — resolve all blockers before release

## MAJOR — Resolve to avoid CONDITIONAL

- [ ] Dependency 'notification-hub' is in_progress / not_validated — confirm integration

## MINOR — Low risk; address if time permits

- [ ] repo-legacy-adapter has quality score below threshold — review static analysis

## Unavailable dimensions

| Dimension | Reason | Action |
|-----------|--------|--------|
| E2E       | No E2E data in brain snapshot | Re-assess after E2E run |
```

### 8.5 SQLite history (`data/local/rrr.sqlite`)

Every run without `--dry-run` is persisted automatically. The file is created on the first run.

| What's stored | Details |
|---------------|---------|
| Assessment record | run_id, release, verdict, score, confidence, assessed_at |
| Per-dimension results | score, evidence, risk factors, rationale per dimension |
| Trend | Delta vs previous run — shown in all output formats |
| RAG index (optional) | Chroma vector index in `data/local/chroma/` if `chroma_path` is set |

Browse with **DB Browser for SQLite**, **VS Code Database Client** extension, or any SQLite tool.
The database exists only after the first real (non-dry-run) assessment.

**Default path:** `./data/local/rrr.sqlite`  
**Override in config:** `memory.sqlite_path: "./data/local/my-custom.sqlite"`

## 9. Understanding the verdict

### Dimension weights and sources

| Dimension | Default weight | Data source | What it measures |
|-----------|---------------|-------------|-----------------|
| **Test Readiness** | 27% | brain JSON | Code quality (sq_avg), defect trend, E2E pass rate |
| **Scope** | 23% | brain JSON | Story points closed / total; scope creep detection |
| **Environment** | 18% | `environment.json` | Infrastructure provisioning readiness |
| **Operational** | 10% | `operational.json` | Deployment pipeline health and rollback readiness |
| **Dependency** | 13% | `dependency.json` | Upstream dependency completion and integration |
| **Estimation** | 9% | brain JSON | Earned-value variance (planned vs actual SP) |

Weights sum to 1.0. Unavailable dimensions have their weight redistributed proportionally
across the available ones — the score stays comparable across different data availability states.

### Score → verdict band

| Score | Verdict |
|-------|---------|
| ≥ 80 | **GO** |
| 40–79 | **CONDITIONAL** |
| < 40 | **NO_GO** |
| < 4 of 6 dimensions available | **INCOMPLETE** |

### Gate overrides (ADR-0013)

Gates can **cap** the verdict regardless of score. The most restrictive gate wins.

| Trigger condition | Cap applied |
|-------------------|------------|
| Any component `stability: down` | NO_GO |
| Any open blocker defect | NO_GO |
| E2E pass rate < 50% | NO_GO |
| Any dependency `integration: failed` | NO_GO |
| `deployment_pipeline: red` | NO_GO |
| `change_freeze: true` | NO_GO |
| Any component `stability: degraded` | CONDITIONAL |
| Any dependency `completion: not_started` | CONDITIONAL |
| Scope creep > 10% across snapshots | CONDITIONAL |
| Open critical defects > 0 | CONDITIONAL |
| `deployment_pipeline: yellow` | CONDITIONAL |
| `rollback_plan: none` | CONDITIONAL |

### Required dimensions (ADR-0015)

If a required dimension is unavailable, the verdict is **capped at CONDITIONAL** even when the
score band says GO. Default required: `[test_readiness, environment]`.

For the OSM config (`configs/osm.yaml`) this is relaxed to `[test_readiness]` so assessments
work even when `environment.json` is a stub file.

### Test Readiness sub-scores

Test Readiness is itself a weighted composite:

| Sub-score | Weight | Derived from |
|-----------|--------|-------------|
| Code quality | 40% | `sq_avg / 3` (brain JSON; 0–3 scale) |
| Defect trend | 30% | Direction of last-5 open-defect series (declining=1.0, flat=0.5, rising=0.0) |
| E2E pass rate | 30% | `passed / (passed + failed)` from `e2e_latest` |

When `e2e_latest` is absent (only ~4 of 41 OSM releases have E2E data), the E2E weight is
dropped and the remaining two sub-scores are renormalised (40→57%, 30→43%) with confidence
capped at 50%.

## 10. Programme filtering and dependency discovery

### Background

The RKT HTML report covers **multiple programmes** in a single file. There is no separate
`programme` field — the code is embedded in the release name string (prefix, suffix, or
embedded token). `rrr-ingest` parses and stores it.

**Programme breakdown in a typical OSM HTML report (41 releases):**

| Programme code | Count | Pattern | Example |
|----------------|-------|---------|---------|
| OSM | 22 | No prefix (native) | `Fund to Fund` |
| AIMS | 6 | `AIMS - ` prefix | `AIMS - RetirePlus RC/RCP` |
| ME&Q | 4 | `(ME&Q)` suffix | `Meeting Scheduler (Full) (ME&Q)` |
| R5 | 3 | `R5 ` prefix | `R5 IS - DT Terminations Cash Withdrawal` |
| EIMS | 2 | `EIMS - ` prefix | `EIMS - AM F2F, AM RCRCP` |
| PIMS | 1 | `PIMS - ` prefix | `PIMS - Terminations Cash Withdrawals` |
| R6 | 1 | `R6 ` prefix | `R6 PIMS - RetirePlus Pro` |
| NEO | 1 | `(NEO)` suffix | `First Time Access (NEO)` |
| R@W | 1 | `R@W` embedded | `First Time Access with Self Enrollment; R@W` |

### Filtering `--list-releases` by programme

```powershell
# All 41 releases (with programme tags)
rrr --list-releases --value-stream "OSM" --config configs/osm.yaml

# Only OSM-native releases (22)
rrr --list-releases --programme OSM --value-stream "OSM" --config configs/osm.yaml

# Only AIMS releases (6)
rrr --list-releases --programme AIMS --value-stream "OSM" --config configs/osm.yaml
```

Output format with tags:
```
Releases in 'OSM' — programme: OSM (22 total):
  [OSM]      RetirePlus RC/RCP Enrollment
  [OSM]      Fund to Fund
  [OSM]      Associate Desktop + CSCO IVR  → dependency for DIST | enables: Terminations Cash Withdrawals
  ...
```

### Scoping fuzzy matching to one programme

When a partial name is ambiguous across programmes, add `--programme` to scope the search:

```powershell
# "Fund to Fund" matches 2 releases (OSM + AIMS) → ambiguity error without --programme
rrr --release "Fund to Fund" --programme OSM --config configs/osm.yaml --dry-run
# → correctly matches "Fund to Fund" (OSM-native)

rrr --release "Fund to Fund" --programme AIMS --config configs/osm.yaml --dry-run
# → correctly matches "AIMS - MMO Fund to Fund"
```

### Dependency/enabler releases

Two releases in the OSM HTML are **enabler releases** — they exist to unblock another release
in a different programme. Their `ir_name` encodes this as `(Dependency for: X; Launch: Y)`:

```
Associate Desktop + CSCO IVR
    → dependency for: DIST
    → enables: Terminations Cash Withdrawals

Onboarding Automation
    → dependency for: OS&M
    → enables: RetirePlus Pro Target Date (Adopt & Manage) DCI & Partial STP
```

These appear in `--list-releases` with a `→ dependency for … | enables: …` annotation.
The relationship is also stored in `brain/OSM-history.json` under `release_relationship`
and appears in `--format json` output.

## 11. LLM providers

The LLM writes **rationale text only** — it never influences the numeric score or verdict.
The default provider requires no model and no configuration.

| Provider type | Configured as | When to use |
|---------------|--------------|-------------|
| `rule_based` | default | No model needed. Produces template-based rationale. Best for CI/scripting. |
| `local_llm` | `type: local_llm` | Ollama on `127.0.0.1`. Produces AI-written narrative. Requires Ollama running. |
| `mock_llm` | `type: mock_llm` | Pre-authored fixture responses. Full guardrail chain, no model. Best for demos. |
| `bedrock` | `type: bedrock` | **Phase 2 opt-in** — Amazon Bedrock Converse API. Requires AWS credentials. `pip install rrr[cloud]`. |
| `claude` | `type: claude` | **Phase 2 opt-in** — Anthropic API (`claude-opus-4-8` default). Requires API key. `pip install rrr[cloud]`. |

### Using Ollama for AI-written rationale

## 14. Troubleshooting

### `VERDICT: INCOMPLETE` — assessment did not fully run

Run with `--verbose` to see the underlying errors on stderr.

| Symptom in `--verbose` | Cause | Fix |
|------------------------|-------|-----|
| `N releases match '…' — be more specific` | Fuzzy match hit multiple releases | Add `--programme OSM` or use exact name from `--list-releases` |
| `no release matches '…'` | No release found at all | Check name with `--list-releases`; check `--value-stream` matches brain file |
| `brain file not found for value stream` | Wrong `--value-stream` or brain dir | Check `brain/` contains `<value-stream>-history.json`; check `--value-stream` |
| `ToolInvocationError` on `environment_source` | `data/environment.json` missing or invalid | Check file exists, valid JSON, correct field names |
| `ToolInvocationError` on `dependency_source` | `data/dependency.json` missing or invalid | Check file exists, valid JSON, correct field names |
| `ToolInvocationError` on `operational_source` | `data/operational.json` missing or invalid | Check file exists, valid JSON, correct field names |
| Fewer than 4 dimensions available | Multiple tools failed | Check errors above; at least 4 of 6 dimensions must succeed |

### `ValidationError` during `rrr-ingest`

| Error message | Cause | Fix |
|---------------|-------|-----|
| `Could not find '__REPORT__'` | Not a valid RKT HTML report | Save the full page (File → Save As → Complete Web Page) |
| `sq_avg` field validation | Rare; clamped automatically | File a bug if this recurs |
| `pv_latest.planned` | Handled; `ge=0.0` allows zero | File a bug if this recurs |

### Environment/dependency `ValidationError`

The most common cause is wrong field names. Use these exactly:

```json
// environment.json
{ "components": [
    { "name": "…", "provisioning": "provisioned", "stability": "stable" }
] }

// dependency.json
{ "dependencies": [
    { "name": "…", "completion": "complete", "integration": "passed" }
] }

// operational.json
{ "deployment_pipeline": "green", "rollback_plan": "documented", "change_freeze": false }
```

**Common mistakes:**

| Wrong | Correct |
|-------|---------|
| `"status": "provisioned"` | `"provisioning": "provisioned"` |
| `"status": "stable"` | `"stability": "stable"` |
| `"status": "complete"` | `"completion": "complete"` |
| `"status": "passed"` | `"integration": "passed"` |
| `"pipeline": "green"` | `"deployment_pipeline": "green"` |
| `"rollback": "documented"` | `"rollback_plan": "documented"` |

### UTF-8 BOM error when creating JSON files in PowerShell

PowerShell 5.1's `Out-File` and `Set-Content` add a BOM that Python's `json.load` rejects.
Use .NET directly:

```powershell
$content = '{"components":[{"name":"app","provisioning":"provisioned","stability":"stable"}]}'
[System.IO.File]::WriteAllText(
    "$PWD\data\environment.json",
    $content,
    [System.Text.UTF8Encoding]::new($false)   # $false = no BOM
)
```

### SQLite "unable to open database" in a browser tool

The database file is created on the **first real (non-dry-run) assessment**. Run without
`--dry-run` at least once, then open `data\local\rrr.sqlite`.
